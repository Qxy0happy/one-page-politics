第 1 课 · 约 9 分钟（含测验）

先看主线：这套技能是一条流水线

数十个技能无需记忆。需要练习的判断只有一项：当前处于哪个阶段，下一步应执行哪个命令。

Matt Pocock 把这套技能定位为「真实工程，而非氛围编程」。它与 GSD、BMAD、Spec-Kit 的区别不在功能多少，而在谁掌握流程：那些框架接管流程，这套技能把流程拆成小步，每一步由你在合适的时机触发。技能本身很小，可以改，可以组合。

由此得到一个直接推论：使用这套体系的能力，等于阶段判断的能力。记不住命令名无关紧要，判断错阶段才是真正的失败——在错误的阶段执行 /implement，比不执行更糟。

一、先分清谁在调用

谁调用 例子 对你的要求
你主动调用 grill-with-docs、to-spec、to-tickets、implement、wayfinder、triage、retro、ask-matt 在正确的时机主动输入；模型不会主动调用它们。
模型自动调用 tdd、code-review、prototype、research、diagnosing-bugs、domain-modeling、codebase-design 通常无需干预；必要时可显式指定。

这条分界体现在技能元数据中：编排型技能带 disable-model-invocation，因此模型不会自动触发。这也是为什么你必须记住主线——主线上的每一步都属于第一类。

本机观察：技能安装在 ~/.agents/skills，撰写本课时共 78 个（含 Flutter、Dart 等非本体系技能）；在 omp 中以 /技能名 调用。系统提示仅列出模型可自动选用的技能，编排型技能不出现，这属于正常现象，并非未安装。

二、主线：从想法到交付

  • /grill-with-docs：通过访谈澄清想法，同时将术语沉淀进 GLOSSARY.md，并将难以回退的决定写入 ADR。没有仓库时改用 /grill-me，访谈流程相同，但不产生文件。
  • /to-spec：明确不再访谈，只将已经谈成的对话整理为规格，并发布到 issue tracker。其性质是压缩，而非第二轮讨论。
  • /to-tickets：拆分为 tracer-bullet 任务单，每张声明其阻塞关系。任务单是自足的，因此最后一张的上下文可以丢弃。
  • /implement：每张任务单使用独立的上下文，内部驱动 /tdd（红-绿-重构），收尾执行 /code-review（标准与规格两轴），然后提交。
  • /retro：改进对象是代理的工作环境——导航、自动检查、编码标准、工具——而非刚完成的代码。

两个变体：可在一步内完成的小改动，在 /grill-with-docs 之后直接执行 /implement；若希望一次性并行推进整份规格，则使用 /implement-spec，它将任务单视为任务图，在就绪边界上并行运行子代理，最终落在同一个集成分支上。

三、入口与岔路

  • /triage：处理他人提交的原始报告，将其推进至 agent-ready。由 /to-tickets 拆分出的任务单已处于 agent-ready，不应再次分诊。
  • /diagnosing-bugs：顽固缺陷与性能回退。在建立「对该缺陷已经失败」的反馈回路之前，它不会提出假设；修复后补充一条回归测试。
  • /wayfinder：当工作量超出一次会话的容量、且路线尚未清晰时使用。它在地图上产出决策而非交付物；地图清空后并回 /to-spec，不应直接进入 /implement。
  • /prototype：某个问题无法在纸面上回答、必须实际运行才能确定，则制作一次性原型；通过 /handoff 进出主线，原型本身保留在分支上作为一手证据。

四、阶段边界只有五个选项

「阶段」指一段工作：本次访谈、本轮实现、本轮检查。阶段结束时，按下列顺序判断，第一个成立的条件即为答案。顺序本身即是重点：/compact 是默认选项，但不应首先考虑。

顺序 选项 成立条件
1 继续 下一阶段需要这一段的原始推理，或上下文还剩约 150k token 的锐利区间
2 /clear 这一段对后续完全无用；代价最低，且旧会话仍可恢复
3 /handoff 换 harness、换目录、交给同事，或中途分叉旁支任务
4 子代理 任务足够紧，可以离线完成，例如自动评审
5 /compact 其余情况；要给压缩指令，说明下一阶段需要什么

除「继续」以外，其余每个动作都将一手来源替换为二手摘要：信息更少、噪声更少、可操作空间更大。被压缩的内容往往是「为什么」，而这恰好无法通过阅读代码恢复。

五、在 omp 中如何开始

ls ~/.agents/skills | wc -l
# 本机：78 个
# 不确定应使用哪个技能时：
/ask-matt
# 已知所处阶段时，直接执行主线命令：
/grill-with-docs

/ask-matt 是这套体系自带的路由器：描述你的处境，它会指向具体技能，并提醒哪些步骤不应跳过。

六、练习

六道情景题。答错后立即显示解释；完成后可重做一遍，第二遍的回忆才形成长时记忆。

1. 哪一组技能可以由代理自己决定调用？

纪律层（tdd、code-review、diagnosing-bugs 等）由模型在任务匹配时取用；编排层带 disable-model-invocation，必须由你输入。

2. 仓库里只有一个模糊想法，主线第一步做什么？

主线从访谈开始：它同时产出对齐后的想法、术语表和决策记录。规格是访谈之后的压缩产物。

3. to-spec 与当前对话的关系是？

to-spec 的定义就是「不访谈，只综合已经讨论过的内容」。补充问题属于上一步 grill-with-docs。

4. wayfinder 的地图清空后，下一步是什么？

wayfinder 产出决策而非交付物；to-spec 将相互关联的决策收敛为可构建的计划，然后才拆分任务单。直接实现会丢失决策之间的联系。

5. implement 处理一张任务单时，内部驱动什么？

每张任务单使用独立上下文：先红-绿-重构，收尾进行双轴评审（仓库标准、原始规格），最后提交。

6. 下一阶段不再需要本段的推理，边界上选哪个？

clear 是代价最低的动作：不消耗时间，归还整个窗口，旧会话仍可恢复。但它会清除与后续相关的上下文，且无法恢复，因此仅当「确实无关」时使用。

七、作业

选择一个真实仓库（本次不使用「一页纸」项目）。暂不执行任何操作，只写下三行：

当前阶段：____（想法 / 规格 / 拆任务单 / 实现 / 收尾）
下一个命令：____
理由：____

写完后将这三行提交给代理，请其按 /ask-matt 的判据复核。若判断不一致，差异通常出现在「是否属于多会话」与「哪些问题必须在纸面上解决」这两处——记录分歧，下一课从这里开始。

若任一步骤不清楚，请直接询问。我是本课教师，可将任一技能讲解至源码级别的细节。
